# Optional cloud portfolio deployment

**Status: not deployed by this repository.** No provider account, credential, network rule, identity, service, or live deployment is created or validated here.

The original Coursera lab runs in the IBM Skills Network lab environment with Docker and GitHub Actions; it does not require public-cloud deployment. This is an optional portfolio extension for synthetic demo data only.

## Target and limits

Target topology: Render Free Docker web service, Aiven Free MySQL, and MongoDB Atlas Free. Free tiers can sleep or cold-start and have limited storage, connections, throughput, and availability. They are not production infrastructure, do not provide an SLA, and are not suitable for real patient data or healthcare-compliance claims.

Render builds the Docker image from selected source. The Phase 3 GitHub Actions candidate proves its own build inputs and image metadata, but it is not provably byte-identical to Render's rebuilt image. See [release readiness](../docs/deployment/release-readiness.md).

## Prerequisites

- A GitHub repository containing this code, plus user-controlled accounts and acceptance of terms for the three providers.
- A protected GitHub Environment named `demo`, with a required reviewer and `main` as its only deployment branch. It has no required secrets or variables.
- A secure secret manager for provider credentials and generated secrets. Enter them only through provider-managed secret fields; do not commit them, put them in screenshots or tickets, or type them into shell history.
- A public HTTPS origin for the deployed application. `CORS_ALLOWED_ORIGINS` must contain exact public origins only: no wildcard, localhost, loopback, or private origin.

## Ordered setup

1. **Create data services and identities.** Create an Aiven Free MySQL service and application database. Create two different least-privilege MySQL identities: one runtime identity for `DB_USERNAME`/`DB_PASSWORD`, and one Flyway migration identity for `FLYWAY_DB_USERNAME`/`FLYWAY_DB_PASSWORD`. Use the Aiven TLS JDBC settings in both `DB_URL` and `FLYWAY_DB_URL`; TLS remains required. Do not reuse the two usernames.

   Create an Atlas Free cluster and an application database user with `readWrite` on the target database. Do not add permanent wildcard network access while creating either data service.

2. **Create Render service.** Create a Render Blueprint from [render.yaml](../render.yaml), or manually create equivalent Free Docker web service using [app/Dockerfile](../app/Dockerfile). Keep `autoDeployTrigger: off`; deployments are selected and started manually. Keep health check path `/actuator/health/readiness` and one instance during bootstrap.

   Creating the Blueprint/service can cause an initial deploy before every required value exists. That deployment is expected to fail closed with cloud configuration validation and is **not** a healthy baseline. Do not treat it as a runtime failure to bypass or fix by weakening validation.

3. **Configure network access from Render's actual service.** In that Render service, use **Connect → Outbound CIDR ranges**. Add those current ranges to Aiven and Atlas network allowlists. Do not leave `0.0.0.0/0` or `::/0` in place; if a narrow temporary rule is needed for a smoke check, remove it immediately afterwards. This occurs after service creation because only that service exposes its usable outbound ranges.

4. **Set managed values.** In Render, provide these operator-managed keys with values obtained or generated by the operator. Names below are exact; no values belong in this guide or repository:

   `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `FLYWAY_DB_URL`, `FLYWAY_DB_USERNAME`, `FLYWAY_DB_PASSWORD`, `MONGODB_URI`, `JWT_SECRET`, `CORS_ALLOWED_ORIGINS`, `APP_VERSION`, and `APP_REVISION`.

   Blueprint-fixed values are `SPRING_PROFILES_ACTIVE=cloud`, `APP_ENVIRONMENT=cloud`, `JWT_EXPIRATION=PT1H`, `JAVA_TOOL_OPTIONS`, and `APP_BOOTSTRAP_ENABLED=false` by default. During one-instance bootstrap only, add the `APP_BOOTSTRAP_*` identity and credential values, temporarily override `APP_BOOTSTRAP_ENABLED` to `true`, then restore it to `false` before removing bootstrap passwords. Cloud validation requires nonblank database, Flyway, MongoDB, JWT, CORS, version, revision, and environment keys; it rejects duplicate runtime/Flyway usernames. It also requires a JWT secret of at least 32 UTF-8 bytes and rejects local/demo/test-like values. Cloud disables demo data, Swagger UI, and OpenAPI JSON. Details: [cloud profile](../app/src/main/resources/application-cloud.properties), [validator](../app/src/main/java/com/project/back_end/config/CloudEnvironmentValidator.java), and [environment template](../.env.example).

5. **Bind release candidate and deploy.** From `main`, run the manual `Phase 3 Release Readiness` workflow and retain its candidate manifest. Record its `sourceCommit`, `expectedAppVersion`, image ID, archive SHA-256, and the current successful Render deploy reference before changing Render. In Render, manually deploy the exact `sourceCommit`; set `APP_REVISION` to that commit and `APP_VERSION` to `expectedAppVersion`. Approve the protected `demo` smoke gate only after that Render deployment completes. The workflow does not deploy or access provider credentials.

6. **Bootstrap once.** For a first authenticated synthetic demo journey, set all `APP_BOOTSTRAP_*` identity and credential keys and temporarily override `APP_BOOTSTRAP_ENABLED` to `true` for one selected deployment with one application instance. Bootstrap creates the single admin and doctor only when absent. A rerun succeeds only when existing identities exactly match supplied bootstrap data; it does not repair, replace, or add to existing identity state. Verify log status reports only `admin=created|existing` and `doctor=created|existing`, then verify both identities.

   Next, restore `APP_BOOTSTRAP_ENABLED` to `false` and wait for a healthy restart. Only then remove both bootstrap password values, then verify another healthy restart. This order prevents a bootstrap-enabled restart without its required password values. Source: [bootstrap configuration](../app/src/main/java/com/project/back_end/config/CloudIdentityBootstrapConfiguration.java) and [bootstrap properties](../app/src/main/java/com/project/back_end/config/properties/BootstrapProperties.java).

## Verify and demonstrate

Use only an unauthenticated, public HTTPS root URL with the protected smoke gate. It verifies:

- `/actuator/health/liveness` is `UP`.
- `/actuator/health/readiness` is `UP` and includes database and MongoDB readiness.
- `/actuator/info` matches selected revision and version, `cloud` environment, `synthetic` data, and no SLA marker.

The smoke check follows no redirects and does not send authentication or provider headers. Its contract is in [scripts/smoke-demo.mjs](../scripts/smoke-demo.mjs). After smoke passes, use only synthetic data for the journey: create a doctor, register/sign in a patient, book a future slot, then record a prescription as that doctor. Do not use real patient data.

## Rollback and troubleshooting

Rollback is limited to manually redeploying the recorded previous successful Render deploy, then rerunning readiness and `/actuator/info`. Do not edit an applied Flyway migration; correct it with a new migration. A Render rollback cannot undo data already changed in MySQL or Atlas, and it cannot prove the prior deployment remains compatible with current data.

If startup fails, use the listed key names from the cloud validator to find missing or invalid configuration without exposing values. Check that runtime and Flyway usernames differ, Aiven JDBC settings keep TLS required, Atlas access is limited to current Render outbound CIDRs, and bootstrap is disabled before removing bootstrap passwords. Do not broaden network access permanently, disable validation, enable automatic deploys, log configuration, or paste secrets into diagnostics.
